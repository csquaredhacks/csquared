# The API pod was killed for using too much memory

- **When:** 15:18 to 15:21 Mountain Time (22:18 to 22:21 UTC), 9 November 2026
- **Planned or real:** planned. This is the runbook's out-of-memory incident: we lowered the
  memory limit on purpose so Radar had something real to investigate.
- **Where:** cluster `csquared` (EKS, Kubernetes v1.34), namespace `hallway`,
  Deployment `hallway`, image `ghcr.io/csquaredhacks/hallway:latest`
- **Tool used:** Radar Cloud, through its MCP server from Claude Code: `patch_resource`,
  `wait_for`, `diagnose`, then a Radar AI investigation (`start_investigation`)
- **Public URL during the incident:** https://stuck-clicking-wooden-verse.trycloudflare.com
  (Cloudflare quick tunnel from the `hallway-tunnel` Deployment; it changes if that pod restarts.
  `make url` prints the current one.)
- **Radar investigation:** id `chat_Sna1LQHpSQgjyNSa`, cluster id `aopPFlGFGNg`, started
  22:19:01 UTC, status `done` at 22:20:28 UTC. Team members with access to our Radar Cloud
  organization can open it under the `csquared` cluster, Investigations.
- **Pods:** crashing `hallway-6cdcd6b8b4-5rsdp` (new ReplicaSet); serving throughout
  `hallway-675698467d-pjlzq` (old ReplicaSet)

## Check it yourself

```bash
curl https://stuck-clicking-wooden-verse.trycloudflare.com/healthz
```

Expected: `{"ok":true,"es":"green"}`. With Radar connected, `kubectl radar` (or the Radar Cloud
UI) shows the Deployment's change history, including both memory patches at 22:18:23 and
22:20:53 UTC.

## What we did

1. **22:18:23 UTC** Patched the `hallway` container's memory to `requests: 48Mi, limits: 48Mi`
   (it was `requests: 128Mi, limits: 256Mi`). A dry run first showed exactly those two changes.
   This is the same change `make oom-demo` makes through Helm.
2. Radar's `wait_for` reported the rollout **blocked**: the new pod was in `CrashLoopBackOff`.
3. Radar's `diagnose` on the new pod showed the cause directly:
   `lastState.terminated.reason: OOMKilled`, `exitCode: 137`, started 22:18:50, killed
   22:18:53 (3 seconds), `restartCount: 2` and rising, `limits.memory: 48Mi`.
4. **22:19:01** Started a Radar AI investigation on Deployment `hallway`. It finished at
   **22:20:28** (87 seconds).
5. **22:20:53** Applied the fix Radar recommended: memory back to `128Mi` / `256Mi`, the values
   in `deploy/chart/hallway/values.yaml`, so the live Deployment matches the Helm release again.
   The rollout completed at once on the original ReplicaSet.

## What Radar said

> **Summary:** Hallway's new pod is OOMKilled in a crash loop after its memory limit was cut
> from 256Mi to 48Mi, half the Deployment stuck unavailable.
>
> **Root cause:** A spec change at 22:18:23 lowered the `hallway` container's memory limit and
> request from 256Mi/128Mi to 48Mi. The new ReplicaSet's pod now hits that ceiling almost
> immediately after starting and is OOMKilled (exit code 137), so it never becomes ready [...]
> The pod's container status shows this directly: terminated with reason OOMKilled after
> running only 3 seconds, restart count climbing during this check.
>
> The old pod (still on the previous ReplicaSet, under the old 256Mi limit) is healthy — its
> logs show clean `/healthz` 200s and a working vector-DB connection — so this isn't an
> application bug or bad image, it's the memory ceiling being set below what the process
> actually needs.
>
> **Fix:** Restore the `hallway` Deployment's container memory limit/request to the prior,
> higher value (e.g. 256Mi limit).
>
> Certainty: likely (confidence 0.85). Unresolved: whether the old pod would also be killed
> under 48Mi was not tested.

Radar found the trigger from its own change history (the spec change 46 seconds before it
looked), not from anything we told it. It also checked the other explanation, a bad image or
an application bug, and ruled it out from the old pod's logs.

## Root cause

The memory limit (48Mi) was below what the Python API needs to start. The kernel killed the
process three seconds in, every time.

## Effect on users

None. The Deployment runs one replica with a rolling update, so Kubernetes kept the old pod
serving until a new one became ready, which never happened. The public URL answered
`/healthz` with `{"ok":true,"es":"green"}` before, during and after the incident.

## Time to fix

2 minutes 30 seconds from the bad change to the fix, of which the investigation took 87
seconds.
